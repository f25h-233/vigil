# QQ 数据库结构笔记

> 全部为本机实测（QQ `9.9.31-49738`，2026-09-13）。
> 仅在实测确认后记录，未验证的推测一律标明。

---

## 一、加密方式

- 库文件前有 **1024 字节假头**，魔数为 `"SQLite header 3"`（注意：**不是**真 SQLite 的 `"SQLite format 3"`）
- 假头之后才是 SQLCipher 数据。剥掉 1024 字节后用 `sqlcipher3` 打开
- PRAGMA 顺序敏感（顺序错则解密失败）：

```sql
PRAGMA cipher_page_size = 4096;     -- 必须在 key 之前
PRAGMA key = '<16位密钥>';
PRAGMA kdf_iter = 4000;
PRAGMA cipher_hmac_algorithm = HMAC_SHA1;
PRAGMA cipher_kdf_algorithm = PBKDF2_HMAC_SHA512;
```

## 二、坏页——触发条件与**页级**影响面

`nt_msg.db` 里存在真实坏页（`database disk image is malformed`）。是否报错**取决于查询计划**：

| 查询形态 | 结果 |
|---|---|
| 无索引列上的 `GROUP BY` / 全表扫描 | ✗ `malformed` |
| `WHERE "40027" IN (15 个群号)` | ✗ **0/5 成功，100% 稳定复现**——`IN` 让优化器放弃索引 |
| `WHERE "40027" = <单群号>`（走 `idx40027_*`） | ✓ 基本正常（15 群中 14 群一次读完） |
| 同上 + 回表取 `40800` 正文 | ✓ 正常 |
| `WHERE "40027"=? AND "40001" BETWEEN ? AND ?`（主键小段） | ✓ 坏区外全部可读 |

**推论**：`1.decrypt.py` 那类"全量导出"永远跑不完（扫全表）；
**按群号逐群 `=` 循环**才能绕开坏页——**不要写 `IN (...)`**。

### ⚠️ 坏页是**页级**损坏——回退的切分粒度决定丢多少

这是 2026-09-13 晚修正的一条：坏页只污染**物理损坏的那几页**，
但 `_read_group` 原回退按 `40058`（**日粒度**）二分，一天内坏一页就让**整天陪葬**。

| 回退策略 | 群 643375490 读出 |
|---|---|
| 旧：按 `40058` 天粒度二分 | 40,947 条（**91.2%**）—— 2026-07-21 整天丢失 |
| 新：按 `40001` **主键**二分（细化到 20 条） | **44,903 条（99.98%）**，仅丢 11 条 |

全 15 群回归：**47,675 / 47,686 = 99.98%**，总耗时 1.0 秒。

**实践教训**：看到"跳过 N 个区段"**不要当成正常输出**——
要拿索引计数与实际读出量对账：

```sql
-- 走索引、不读数据页，所以坏页也数得到 —— 这是"应该有"的条数
SELECT count(*) FROM group_msg_table WHERE "40027" = ?;
```
两个数不一致 = 有行被坏页吃掉了。

## 三、`group_msg_table` 列义（实测）

群消息的真身在 `group_msg_table`，共 38 列，列名是纯数字（SQL 里必须加双引号）。

| 列 | 含义 | 备注 |
|---|---|---|
| `[40001]` | 消息 ID | `INTEGER PRIMARY KEY`，即 rowid。**值域不连续**：前段是小整数，之后跳到 ~7.6×10¹⁸ |
| `[40020]` | 发信人 uid | 形如 `u_m-DGcmJpBZd4wB9FTOCKCQ` |
| `[40021]` | **群号**（TEXT） | |
| `[40027]` | **群号**（INTEGER） | 有 4 个索引，全部以它打头 |
| `[40050]` | **时间戳**（真 unix 秒） | |
| `[40058]` | 时间戳（**日粒度**） | 值形如 `1788192000`（UTC+8 的零点） |
| `[40800]` | **消息正文** | protobuf BLOB |
| `[40003]` | 序号 | 与 40027 组成索引 |

**索引**：
```
idx40027_40003          (40027, 40003)
idx40027_40058          (40027, 40058)
idx40011_40012_40027    (40011, 40012, 40027)
idx40027_40003_40002    (40027, 40003, 40002)  UNIQUE
```

⚠️ `ORDER BY 40058` 会报 `1st ORDER BY term out of range`——裸整数被当成"第 N 个输出列"的序号。
**所有数字列名一律加双引号。**

⚠️ 按 rowid（`40001`）分页会引入 `USE TEMP B-TREE FOR ORDER BY`（每批重扫全群，O(n²)）。
单群直接 `WHERE "40027" = ?` 一次读完最快。

## 四点五、发信人解析（`group_member3`）

`group_info.db` 的 `group_member3` 表是**发信人姓名的正解**（列义由 QQDecrypt 文档确认）：

| 列 | 含义 |
| --- | --- |
| `1000` | nt_uid ← **与消息表 `[40020]` 的值直接对应** |
| `64003` | 群昵称（未设置为空） |
| `20002` | QQ 昵称 |
| `1002` | QQ 号 |
| `64016` | 是否仍在群（0=在群，1=已退群） |

本机 110,105 行（跨全部群），**实测覆盖 96.9% 的 (群号, uid) 组合**。
远好于 `nt_msg.db` 里只有 44 行的 `nt_uid_mapping_table`。

姓名优先级：**群昵称 > QQ 昵称 > QQ 号**（群昵称才是群里认得出的那个名字）。

⚠️ 部分 QQ 昵称含**非法 UTF-8 字节**，默认 `text_factory` 会让整个查询抛错。
必须设 `conn.text_factory = lambda b: b.decode("utf-8", "replace")`。

## 四点六、消息正文提取

`[40800]` 是 protobuf BLOB，提取算法是启发式的（移植自 qqcli 的 `extract_text`）：

1. 扫 `[0x82][0x16]` 标记 → 读 varint 长度 → 取文本字节
2. 校验：含中文字符，或纯可打印 ASCII
3. 都不成 → 退回 GBK 解码整个 BLOB

### 三条提取路径

1. **`0x82 0x16` 标记**（多数普通消息）
2. **连续中文串兜底** —— ⚠️ 这条**必须有**，见下方"踩过的坑 3"
3. **GBK 解码**（旧式编码）

### 本机实测（43,719 条）

| 类别 | 条数 | 占比 |
| --- | ---: | ---: |
| **可读文本** | 40,040 | **91.6%** |
| 非文本 | 3,679 | 8.4% |

`[非文本]` 的构成：

| 子类 | 条数 | 占全库 |
| --- | ---: | ---: |
| 图片引用（blob 内含 `xxx.jpg`，且无文字） | 1,487 | 3.4% |
| 系统事件／纯 @提及（只有 uid 列表） | 2,192 | 5.0% |

**独立复核**（绕开提取器、直接在字节里搜合法 UTF-8 中文序列）确认：
剩余 3,679 条中 **100% 确实不含中文**。即 91.6% 已接近该数据源在纯文本上的可达上限。
要再往上只能 OCR 图片——而纯图片消息只占 **3.4%**（远小于早期误判的 15.8%）。

### 两个踩过的坑（移植时务必注意）

1. **Rust 的 `str::len()` 是字节数，Python 的 `len()` 是字符数。**
   原文 `if result.len() > 3` 在 Python 里直接照抄会丢掉所有**两字短消息**
   （"行吧""好的""收到"）——实测可读率因此从 71.7% 掉到 61.7%。
   已引入 `_blen()` 统一为字节语义。

2. **GBK 兜底会把二进制噪声解成"看似中文"的乱码。**
   protobuf 的字段标记（`0x13`/`0x15`/`0x16`/`0x17`）落在 C0 控制字符区，
   而真实聊天文本不会含控制字符——用这道闸挡住（`_plausible()`）。
   宁可输出 `[非文本]`，也不能输出乱码。

3. **只认 `0x82 0x16` 标记会整类漏掉消息——实测漏了 20 个百分点。**
   有一类消息的文本**不在标记里**，而是散落在其他 protobuf 字段中：
   **撤回提示**（"你猜猜撤回了什么"）、**表情描述**（"动画表情""并坏笑了一下"）等。

   该项早期被漏判为"这些消息本来就没文字"，原因是**先用不充分的方法验证了结论**
   （只看 blob 里有无 `.jpg` 后缀 + 抽样 6 条），而非用独立方法穷举。
   改用「直接在字节里搜合法 UTF-8 中文序列」复核后，发现 12,340 条里有 **8,659 条（70%）含中文**。

   补上路径 2 后：**71.7% → 91.6%**。

   > 教训：判定"数据里没有 X"时，必须用**独立于现有实现**的方法穷举验证，
   > 不能用"我的工具没提取到"当作"不存在"的证据。

## 四点七、图片通知：为什么纯本地拿不到（已穷尽验证）

官方通知（辅导员/班主任）曾有较大比例读不到，一度怀疑是因为**发的是图片**（通知截图）。
把「能不能本地拿到图片」查穿了，结论是**不行**：

| 尝试路径 | 实测结果 |
| --- | --- |
| blob 里的文件名 ↔ 缓存文件名 | ❌ 不同源。缓存名是 `{内容md5}_{尺寸}.{ext}`，blob 里是**服务端 fileid**（如 `7C9204E4D46B206DAAEA8020BF708947.jpg`） |
| `files_in_chat.db` 映射 | ❌ 仅覆盖 **3.1%** 的图片消息，且图片行的 `[45403]`(filepath) 多为空 |
| blob 里内嵌本地路径 | ❌ 仅 **1.5%**（181/12,340），其中文件仍在的只有 97 条，且**绝大多数是 `Emoji/emoji-recv/` 的表情包**，不是通知截图 |

**根因**：QQ **只在用户实际查看过**某张图时才把它缓存到 `nt_data/Pic/<月>/Thumb|Ori`。
辅导员发的截图大多没被点开过，本地根本没有文件。

**唯一可行的覆盖路径**是 blob 里的 CDN 地址：

```
multimedia.nt.qq.com.cn / download?appid=1407&fileid=EhTyj9dR_mOA...
```

但下载需要**联网**（且很可能需要 rkey 授权令牌），**会打破路线 C「不登录、不发言、纯本地零网络」的前提**——
所以是否需要，是一个必须由使用者拍板的架构决策，不是技术问题。

**不联网时的缓解**：部分通知会被班助/热心同学**以文字形式转发**（实测检索「通知」能找到
`储运263班主任助理…` 发布的报名链接与截止时间），这部分已被文本层覆盖。
但并非普遍规律——实测有辅导员整段时间只发图、无人转文字。

### 补上文本提取路径 2 之后，这个问题的规模大幅缩小

| 指标 | 修正前 | 修正后 |
| --- | ---: | ---: |
| 全库可读文本 | 71.7% | **91.6%** |
| 纯图片消息占全库 | 15.8%（误判） | **3.4%** |
| 官方发送者合计可读率 | 45%~65% | **82.4%** |
| 官方消息仍读不到的 | — | 216 条中 38 条 |

**结论：为「3.4% 的图片 + 18% 的官方消息」去联网下载、打破零网络前提，性价比不成立。**
建议接受这部分缺失，把精力放在摘要层。若将来确有需要，CDN 地址可从 blob 提取，届时再评估。

## 五、qqcli-rs 的三个实测局限

（qqcli 是对接工具，以下都是它的问题，不是数据的）

### 1. 群聊数据源找错了表

qqcli 的群聊功能全部读 `dataline_msg_table`（`src/db.rs`、`src/db_index.rs`），
并把 `GROUP_NAME = [40020]` 当会话标识。但**本机 QQ 版本里群消息在 `group_msg_table`**，
`dataline_msg_table` 只有 47 行（是"数据线"功能的消息）。

**对策**（已实现在 `vigil/export.py`）：两表列结构完全相同，所以把群消息复制一份进
`dataline_msg_table`，并将 `[40020]` 覆盖为群号即可。实测 `qq index` 导入 43,641 条、
`qq sessions` / `qq history` 均正常。

### 2. 中文搜索不可用

`qq search` 走 DuckDB 的 `fts` 扩展，其默认分词器对中文无词边界——整条消息成为一个 token，
故单词查询永不命中。且回退逻辑有 bug：

```rust
if let Ok(results) = search_fts(...) { return Ok(results); }  // 空集也是 Ok，回退永远不触发
```

**结论**：VIGIL 的检索自己做。规模上 4.3 万行用 SQLite `LIKE '%…%'` 全表扫即是毫秒级。

### 3. 发信人归属不可靠

`qq history` 把群消息全显示为「我」。qqcli 从 `[40021]` 取"发信人名"，但该列在本机
存的是群号。真正的发信人 uid 在 `[40020]`。

**可补**：源库有 `nt_uid_mapping_table`（本机 44 行），可做 uid → 姓名解析。

## 六、正文解析质量（本机抽样 3000 条）

| 类别 | 条数 | 占比 |
|---|---:|---:|
| 可读文本 | 2,275 | 75.8% |
| 图片（`[image]`） | 493 | 16.4% |
