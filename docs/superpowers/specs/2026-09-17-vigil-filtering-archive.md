## 2. 为什么停：三条实测证据

用户给的理由是「手动删可行 / 噪声影响有限 / 过滤可能降低健壮性 / 投入巨大」。
**其中「降低健壮性」这条有数字**——不是印象：

### 2.1 独立探针两轮都救不活全部

判据用的是 spec §1.2 的 5 条已知好条目，外加**两条真正独立的探针**（源文**不在** prompt 内）：

| 探针 | 源文 | 第一轮干跑 | 上下文修复后 |
|---|---|---|---|
| item 14 | `早自习不知道有没有 反正7点到7:40` | ❌ 死 | ✅ **复活** |
| item 84 | `9.6上午` | ❌ 死 | ❌ **仍死（唯一）** |
| item 86 | `打电话办卡的都别信哦所有人` | ❌ 死 | ✅ **复活** |
| item 111 / 143 | （源文被逐字写进 prompt，**受污染**） | 111 ✅ / 143 ✅ | ✅ / ✅ |
| **item 183**（主独立探针） | 助学贷款「先不要把学费存在学校的这个卡里」 | ✅ | ✅ |
| item 182（次独立探针） | `有人捡到校园卡和钥匙（640）吗` | 判 0 条（被日报引用保下） | 判 0 条（同） |

⇒ **独立探针真实成绩：第一轮 0/2，上下文修复后 1/2。**

⚠️ **注意 86/111/143 是受污染探针**（它们的源文被逐字写进了 prompt）——
**它们存活不构成「判据生效」的证据**。详见 §5 的 R1。

### 2.2 判决有 **10% 量级的噪声**

同一批次**逐字节相同**重放 3 次：

```
产出 items: 7 / 8 / 8
落地集合 Jaccard: 0.67
3/30 = 10% 的消息在三次之间翻转（quote 层面 12 条只有 3 条三次都在）
```

采样参数：`temperature=0.1`、`response_format=json_object`、**无 seed、无 top_p**。

⇒ **「一次重判就删」这个设计，建立在 10% 的噪声上。**

### 2.3 ⭐ 最关键：**53 条删除是「整批放弃」，不是「判为广告」**

把将要删的 100 条按死法拆开：

| 死法 | 条数 | 含义 |
|---|---|---|
| **a2** | **46** | 同批别处有产出、唯独没为这条产出 ⇒ **有批内对照** |
| **a0** | **53** | 所在**整批返回空** |
| quota | 1 | 消息在别处有产出、旧条目超额 |

**a0 的性质被一条实测判死了**：

> **39 个空批的「候选」条数中位 8（均值 9.1、最大 23），与非空批（中位 9、均值 11.7）一样多。**

⇒ 一次 `[]` 是**模型把一整批约 8-9 条「预筛已判定值得抽」的消息集体放弃**
——**那是批次级失灵，不是「批里没东西」**。拿它当删除依据，本来就不该。

（反证也记下：a0 子集 83% 是 life + secondhand、广告味 60%，**确实像「整批真垃圾」**；
但里面仍有 8 条 informational——notice 3 / academic 2 / activity 3，**按批放行会连带删掉**。）

## 5. 未测的缺口（**留给后来者，别当成已解决**）

1. ⚠️ **prompt v3 的生产误杀率从未测过。**
   我们测的是 **repass 重判**（把一个稀疏集重新判一遍），**不是 `refine` 的新判**。
   两者条件不同：`refine` 的中位批是 30 条、`repass`（修复前）的中位批是 **1** 条。
   ⇒ **不要拿 repass 的数字去推断 v3 在新消息上的表现。**
2. ⚠️ **受污染探针**：item 86/111/143 的源文被**逐字**写进了 prompt
   ⇒ 它们存活**不构成**判据生效的证据。真正独立的只有 **183（主）与 182（次）**。
3. ⚠️ **单条判决的稳定性无从推断**：审计字段**无 seed、无 temperature、无重复次数**，
   每批只观测一次。可用的只有 10% 的批级翻转率这个上界。
4. ⚠️ **`_to_item` 的静默丢弃**曾无计数无日志（诊断 E3 发现）。已要求补可见性，
   但**历史干跑的 174 条事后无法逐条复核**。

## 7. 这条线的方法论教训（对 M6/M7 有用）

1. **⭐ 「重判」可能根本不是重判。** `repass` 在稀疏源消息集上重建批次（中位 1 条、63 个单条批），
   而 `refine` 的原判在 ±2 上下文的密批里做（中位 30）——
   **62/311 条被孤立判，`refine` 侧 0/311**。
   ⇒ 修复上下文后**删除量从 174 降到 100**，探针 **14/86 复活**。
   **教训：任何「用新版本重新判一遍」的设计，必须先证明输入条件与原判一致。**
2. **⭐ 「整批返回空」≠「逐条判死」。** 前者是批次级失灵（见 §2.3），
   拿它做决策会误伤；后者有批内对照，可逐条复核。
   **教训：批量判决的失败信号必须按层拆开统计。**
3. **⭐ 抽样噪声必须先量。** 无 seed 的 LLM 调用，**单次判决不是测量结果**。
   先跑一次重放，量出翻转率，再决定要不要「一次定生死」。
4. **⚠️ 我们的量具本身出过三次错**（详见 ledger）：
   - `grep -c $'\r$'` 数行尾 ⇒ **静默假阴性**（对全 CRLF 文件返回 0）；`od -c | grep -c '\r'` 同样不可靠
   - 测试输出「取最后一行」被无关 warning 顶掉 ⇒ **9 个变异体全被判成假绿**
   - 反引号被 shell 当命令替换 ⇒ 在仓库根造了 3 个 0 字节文件
   ⇒ **唯一可信的行尾量具是 `git ls-files --eol`；每条结论都要能被原始输出直接支持。**
5. **⭐ 写得不好的变异体会造出「假红」**，而**假红比假绿更难察觉**（"变红了"看起来就是成功）。
   实测：漏掉替换串里的 `ORDER BY` ⇒ 39 条红全是 `no such column` 崩溃，白追一轮。
   ⇒ **变异体本身正确必须先被验证**；取函数原文要**程序化地从 git 取**，不要手写。
