## 1. 现状实测（本版新增的事实）

本节所有数字**取自 2026-09-16 的真库快照**。按 M4 的教训，**带时刻**：
**快照时刻 2026-09-16 22:30 前后**。库会自己涨，要用请现查。

### 1.1 噪声的真实规模——**spec §4.3 已被违反**

第一版 §4.3 白纸黑字写着「**不产出入库的**：广告（校园卡王、维修蔡师傅一类刷屏）」。
实测：

| 范围 | items | 其中来自办卡号 | 占比 |
|---|---|---|---|
| 全部 | 328 | 46 | **14.0%** |
| 2026-07 | 60 | 16 | 26% |
| 2026-08 | 120 | 34 | 28% |
| 2026-09 | 148 | 2 | 1% |

用户感受到的现场是**点「生活」**：该分类 82 条，其中标题含「卡/套餐/流量」的 **28 条 = 34%**。

**为什么预筛和 prompt 都拦不住**（三处叠加，各有行号）：

1. `prefilter.py:29` 的 `DEFAULT_KEYWORDS` 里有「**办理**」——一条孤立的办卡广告
   （「校园卡办理，需联系」）**非但不会被丢，反而命中保留规则被"保送"进 LLM**。
2. 唯一的反广告规则是**刷屏**（`prefilter.py:90-121`：同群、同 uid、60 秒内 ≥3 条归一化后相同），
   它只认「重复」，**对单条广告无效**。
3. `refine.py:75-82` 的 prompt 里关于丢弃的 3 条规则**全是内容价值判断**
   （闲聊 / 纯提问 / 吐槽附和），**一个字没提商业推广**。

⇒ **这不是"要不要加过滤"的需求，是"第一版的要求没落地"。**

### 1.2 ⭐ **「屏蔽发信人」这个显然的修法，已被实测否决**

四个办卡号的 items 里，**混着 15 条合法信息**，且归因经源文核实**是正确的**：

| item | 标题 | 源消息原文 | 发信人 |
|---|---|---|---|
| 14 | 早自习时间：7:00-7:40 | `早自习不知道有没有 反正7点到7:40` | Aaaa 常大卡王 |
| 84 | 抢课通知时间：9 月 6 日上午 | `9.6上午` | Aaaa 常大卡王 |
| 86 | 警惕冒充校园卡办理人员的诈骗 | `打电话办卡的都别信哦所有人` | Aaaa校园卡王 |
| 111 | 住宿费统一扣除 1500 元 | `住宿费也统一扣1500` | Aaaa校园卡王 |
| 143 | 宿舍最早入住时间：9月5日 | `最早9.5` | 今天有没有人找学姐办卡 |

> **那四个号是真的学生，既卖卡也正常参与对话。**
> 按 uid 屏蔽 = 为删 31 条垃圾赔上 15 条真信息（误杀率 **1:2**）。

**关键词维度同样不行**：`item 182 寻物：校园卡和钥匙`、`item 183 辅导员提醒：办理助学贷款勿提前存学费`
都是好条目，会被「校园卡」「办理」打死。

⇒ **裁定：广告/推广的判据必须落在「消息内容」维度，禁止使用发信人黑名单。**

### 1.3 要素（时间/地点）现状——**分工已经存在，且是对的**

第一版没有明写这条原则，但代码里已经跑着一条清晰的分界线：

| 归 prompt（语义判断） | 归 code（格式 / 证据 / 时序） |
|---|---|
| 这条消息值不值得抽 | `_parse_deadline`（`refine.py:170-188`）**只认 `%Y-%m-%d`** |
| `kind` 是哪一类 | `deadline_supported`（`deadline.py:65-84`）要求源文里**逐字**有带月份的写法，裸「26号」不算依据 |
| `deadline` 该填什么 | `event_ts`（`refine.py:300`）**强制**取源消息时间戳，模型给的值直接忽略 |
| `title` / `detail` 怎么写 | `quote` 必须能逐字匹配到源消息（`_match_source` `refine.py:236-257`） |

**实测抓到两个缺口**（不是"选 prompt 还是选代码"，是这两处漏了）：

| # | 缺口 | 实测证据 |
|---|---|---|
| a | **`place` 零校验**——66/328 有值，却是唯一一个**没有"源文里有没有依据"闸门**的要素 | 对照：`deadline` 有 `deadline_supported`，`place` 什么都没有 |
| b | **`deadline` 不做时序核对** | `item 83`：死线 `2026-05-06`，消息日 `2026-08-05`，**死线比消息早 91 天**——一条已过期三个月的「⏰ 别忘」 |

### 1.4 人物维度所需的数据关系——**uid ↔ uin 是 1:1，可以互查**

用户要求「输入特定人物的 **QQ 号**」，而 `items.actor_uid` 存的是 **uid**。实测这个转换是可靠的：

```
sender_names       5,696 行
distinct uid       4,772
distinct uin       4,681
uid → 1 个 uin     4,766 个 uid   （例外：6 个 uid 有 2 个 uin）
uin → 1 个 uid     4,680 个 uin   （例外：uin=0 有 98 个 uid）
uin 为 null            0 行
```

- **`uin = 0` 是匿名哨兵**（98 行），**必须在人物模型里排除**。
- `messages.sender_uid` 为空的消息占 **2.6%**（1,264 / 49,548）——匿名者，不该被任何人物筛选中。
- **uid 跨群稳定**：卡王 `u_eH9si89UzNPr_2Zh67_Gaw` 在群 643375490 与 949603689 里是同一个 uid、同一个 uin `2874448217`。

**查询侧地基已经在了**——`store.py:690` 的 `_ITEM_JOINS` **已经** LEFT JOIN 了 `sender_names`：

```python
_ITEM_JOINS = (
    " FROM items i"
    " LEFT JOIN sender_names sn ON sn.group_id = i.group_id AND sn.uid = i.actor_uid"
)
```

⇒ 「按人物筛选」= 把 `sn.uin` 加进 `_ITEM_COLS` + 一个 `IN (...)`。**不是新管道。**

### 1.5 前端的真实工作量——**「加主题」不是加开关，是重构**

| 项 | 实测 |
|---|---|
| `web/src/index.css` | **只有 13 行**，全应用只声明 **2 个** CSS 变量（`--color-vigil-bg` / `--color-vigil-fg`） |
| 其余颜色 | **Tailwind 调色板硬编码散落在几十处 className**（`bg-white/5`、`bg-black/30`、`text-sky-400`、`text-amber-400`…），`web/src` 内 `style={{}}` **零命中** |
| 现有主题机制 | `dark:` / `prefers-color-scheme` / `matchMedia` / `localStorage` **全部零命中** |
| **不在 CSS 里的 3 处颜色** | `web/index.html:9` 的 `<meta name="theme-color">`、`vite.config.ts:21-22` 的 manifest `background_color` / `theme_color` |
| 状态持久化 | 无 URL 参数、无 localStorage——**刷新后 tab 与 kind 全部重置**（`App.tsx:15-18`） |

⇒ 主题化 = **把散落的硬编码收成语义变量**，是实打实的重构，不是虚高的估工。

**⚠️ 一个会在 M7 冒烟时以「我改了主题怎么没变」形态出现的坑**：

- `vite-plugin-pwa` 用 `registerType: 'autoUpdate'`，注入的 `registerSW.js` **没有任何 `onNeedRefresh` 钩子**
  （`web/src` 里 `virtual:pwa-register` 零引用）⇒ **已经打开的标签页不会自动刷新**，继续跑旧 bundle。
- `api.py` 的静态托管**未设任何 `Cache-Control`**（全仓零命中）⇒ `/sw.js` 走浏览器启发式缓存，**推迟更新检查**。

### 1.6 ⚠️ M6 的地雷：`#3 加群` 想要的「可选群列表」，现成实现会写 `data/`

`vigil groups`（`cli.py:60-104`）已经做了「列出 QQ 库里所有群 + 是否已纳入」，
Web 端做「新增监视群号」时最自然的做法是复用它。**但它不能直接用**：

```python
# cli.py:63-69
counts = qqdb.list_group_message_counts(
    qqdb.open_encrypted(
        qqdb.strip_fake_header(
            config.qq_db_dir / "nt_msg.db",
            config.output_db.parent / "cache" / "nt_msg_clear.db",   # ← 写 data/cache/
        ), key))
```

`strip_fake_header` 是**就地截断重写**（无临时文件、无原子改名、无锁）——这正是第一版遗留的 **U-4**。
**且它与 `export` 共用同一个缓存文件。** 若 Web 端点直接调它：

1. 会把「Web 侧绝不写 `data/`」这条机械不变量**从后门打破**（`data/cache/` 也是 `data/`）；
2. 与正在运行的 `export` 抢同一个文件——U-4 的最坏后果是**部分消息静默消失、还被报告成「QQ 库物理坏页」**。

⇒ **裁定：`#3` 的群列表必须走一条只读路径**（要么 Open 时不重写缓存，要么列表由 CLI 预生成、Web 只读产物）。
**这条与 U-4 必须在同一个里程碑里解决，不能分开做。**

## 2. 本版的七条裁定（全部由用户 2026-09-16 明确选择或确认）
>
> **D10–D13** 定了第一轮范围；**D14–D16** 是用户当晚追加四条新功能后**重新裁定**的。
> D11 被改过一次——**改的方向是"更精确"，不是"更松"**（详见 §8）。

| # | 裁定 | 内容 |
|---|---|---|
| **D10** | **存量噪声的处理** | **只重抽"已产出 items 的那批源消息"**（约 328 条 ≈ 11 批），**不重抽 4.7 万条全量**。可复现、可验证 v3 判据本身。**已知代价：这些 item 的 `item_id` 会变。** |
| **D11** | **Web 侧的写边界（细化 M3 的不变量）** | ⚠️ **本裁定于 2026-09-16 晚被用户扩范围后重新裁定过一次**（见 D14）。<br>**M3 的「Web 侧绝不写 `data/vigil.db`」细化为**：**Web 侧可写 `config/` 与「人工干预层」（D14），不可写 `data/vigil.db`**。落盘必须是原子写（临时文件 + rename）。`data/vigil.db` **仍然 `mode=ro`**，且**这条继续由测试机械保证**。 |
| **D12** | **里程碑拆分** | **M5 正确性 → M6 配置 → M7 外观**（三版，各自一轮完整六阶段）。 |
| **D13** | **广告/推广的判据维度**（本版新增，由 §1.2 实测推出） | **判据落在「消息内容」维度。禁止使用发信人黑名单/白名单来过滤广告。** 理由见 §1.2：误杀率 1:2。 |
| **D14** | **人工干预层**（用户 2026-09-16 追加范围后裁定） | 人工对**数据**的修改（改分类、删除）**不写 `data/vigil.db`**，而是写入一张 **append-only 的编辑事件表**（独立可写 SQLite，D11 已把它划出只读范围）。<br>**一次解决四件事里的三件**：撤销天然有（事件表可回溯）、手动改分类=一条事件、删除=tombstone 事件。 |
| **D15** | **删除的语义** | **软删**：界面与日报里消失，**库里的行仍在**，且**永不被重抽复活**。<br>与第一版 §8.2 的「**丢弃 ≠ 删除**」是同一哲学。 |
| **D16** | **「重排已有条目」的语义** | **两者都要**：① **LLM 重判**——改了类目定义后，让模型按新定义重判已有条目的源消息；② **人工微调**——界面上多选批量改。<br>⚠️ **两者的结果都写进人工干预层，不改 `data/vigil.db`** ⇒ **`item_id` 不变，R9 自动化解**（见 §6）。 |

## 3. 新增概念

### 3.1 人物（Person）

| 字段 | 口径 | 说明 |
|---|---|---|
| `uin` | **主键，人类口径** | 用户输入的 QQ 号。实测 1:1 可查（§1.4） |
| `uid` | 运行时解析 | **不落配置**——query 时经 `sender_names` 由 uin 反查，避免 uid 与 uin 脱节 |
| `label` | 显示名 | 用户自己起的名（如「辅导员张老师」），**不是**群昵称快照 |
| `note` | 可选备注 | |

- **`uin = 0` 是匿名哨兵，必须拒绝录入。**
- **本版不做「极性」（屏蔽/监视）概念**——D13 已否决 uid 维度用于过滤；
  人物名单的语义**只有一种**：**标记 + 筛选**，不是权限。

### 3.2 配置（Config）

**`config/*.toml` 是唯一真相源，数据库是派生物。** 三份文件：

| 文件 | 现状 | M6 之后 |
|---|---|---|
| `config/groups.toml` | 已有（15 群 + settings） | 可经 Web 增删（原子写） |
| `config/categories.toml` | 已有（7 类） | **可经 Web 增删改**（用户追加范围）+ **版本快照**（供"回滚类目分类"） |
| `config/persons.toml` | **M5 新建** | 可经 Web 增删 |

**LLM 配置**（M6）：只存 **provider 预设 / base_url / model**；**密钥永远不进配置文件**，仍走 `.env`。

### 3.3 人工干预层（Overlay）—— D14

**动机**：用户要「撤销」「手动改分类」「删除」「重排」四件事，其中三件是**写数据**。
直接写 `data/vigil.db` 会打破 D11 的机械保证；而**一张 append-only 的事件表同时给出这四件事**。

**存储**：`data/overrides.db`（独立可写 SQLite，WAL）。
**不放进 `config/`**：它是数据不是配置、会随时间增长，而 `config/` 要进 git、要能导入导出。

**核心表**（形状为设计意图，最终字段名由 M5 计划冻结）：

```
item_edits(
  edit_id, item_id, msg_id, action, field, old_value, new_value, actor, created_at
)
  action ∈ { set_kind, set_field, delete, restore }
```

**两条键，各司其职**（这是本设计的关键）：

| 键 | 稳定性 | 用途 |
|---|---|---|
| `item_id` | **不稳**（重抽会换） | 「改这一条的分类」 |
| `msg_id` | **稳定**（源消息永不变） | 「这条**永不被重抽复活**」（D15） |

⇒ **`refine.py` 在重抽时必须读 overlay 并跳过带 `delete` 事件的 `msg_id`**，否则 D15 只是一句空话。

#### apply 的位置：**在 `store.py` 的查询层，不在消费方**（实测得出的设计）

实测「直接读 `items` 的路径」共 **5 处**（`grep -n "FROM items\|JOIN items" vigil/*.py` 命中 7 行，
其中 `store.py:762` 是 FTS 子查询、不是读路径）：

| 位置 | 是什么 | 谁消费 |
|---|---|---|
| `store.py:372` | `window_items`（时间窗取条目） | **`digest.py` 的日报合成** |
| `store.py:691` | `_ITEM_COLS/_ITEM_JOINS` 主查询 | `search_items`（→**`api.py` 的 `/api/items`**）、`get_item`（→`/api/items/{id}`） |
| `store.py:801` | `COUNT(*)` 分页总数 | `/api/items` 的 `total` |
| `store.py:846` | `kind_counts` 类目统计 | `/api/items` 的类目计数 |
| `cli.py:518` | `SELECT title FROM items` | `deadline-audit` 的核对输出 |

**关键实测发现**：`digest.py` **不直接读 `items`**——它走 `store.window_items`。
⇒ 所以正确做法是**把 overlay 的 apply 收敛在 `store.py` 的这几个查询函数里**，
而不是在 `api.py` / `digest.py` 各打一个补丁。**一处生效，所有消费方自动继承。**

> 若反过来在消费方 apply，就是 R13 的温床：**漏掉的那一处不会有任何测试变红**。
> （M4「记下来了 ≠ 派下去了」的同族。）

**撤销**：因为 append-only，「撤销」= 追加反向事件 / 丢弃尾部事件。
**类目配置的回滚**是另一件事（`config/categories.toml` 的版本快照），两者都做，别混为一谈。

**⚠️ 边界**：overlay 是**视图层修正**，不是"数据被改真了"。这个性质要在 spec 里说清，
否则将来有人直接 `sqlite3 data/vigil.db` 查，会发现"删除的条目还在"。

### 3.4 「要素」的归属判据（把 §1.3 的隐含原则写死）

> **语义判断归 prompt；格式、证据、时序归 code。**
>
> 新增任何要素字段时，必须先回答两个问题：
> ① 这个值是**模型"看出来"的**吗？（是 → prompt）
> ② 这个值**能不能在源文里找到依据 / 能不能与已知事实对账**？（能 → **必须有 code 闸门**）
>
> **判据：任何一个新要素字段，如果没有 code 层的证据闸门，它就不算做完。**

## 4. 架构改动

### 4.1 M5 · items 的正确性与可筛选性

```
① 噪声治理
   ├ prompt v3：新增一条「商业推广 / 代理招募 / 办卡广告 → 不入库」（D13：内容维度）
   ├ prompt_ver: v2 → v3（改 prompt 必须升版本，这是第一版的既有纪律）
   └ 存量重判（D10）：scope = 已产出 items 的源消息，一次一命令
       ⚠️ **语义是"只删不换"，不是"整批替换"**（见 R9 的实测）：
         · 新判为推广/丢弃 → 删除对应旧 item
         · 新判为仍产出   → **保留旧 item 不动**（避免 item_id 翻新打断 digest_items）
         · 被 digest_items 引用的 → **跳过并报告**，不静默处理
       ⇒ 产出一张「删了哪些 / 保留了哪些 / 跳过了哪些」的可核对清单

② 要素闸门（§3.4 判据）
   ├ place：补证据闸门（对齐 deadline_supported 的做法）
   └ deadline：补时序闸门（死线早于消息时间 → 降级为 None，与既有的"降级不删条目"一致）

③ 人物维度
   ├ config/persons.toml（新建，§3.1 模型）
   ├ store：_ITEM_COLS 加 sn.uin；_item_filters 支持 actor_uin IN (...)
   ├ api：/api/items 的 kind 改多值（kind IN (...)）+ 新增 actor_uin 多值
   └ web：分类条目「按人物筛选」——复选，与既有类目体系**维度内并集、维度间交集**

④ ⭐ 人工干预层（D14，M5 的架构中心）
   ├ data/overrides.db + item_edits 表（append-only）
   ├ 手动改分类（set_kind）/ 软删（delete）/ 撤销（restore）
   ├ ⚠️ refine.py 重抽时读 overlay 跳过 tombstone 的 msg_id（D15 的落地，不可省）
   └ ⚠️ apply **收敛在 store.py 的查询函数里**，不在消费方打补丁（§3.3 的表：5 处真读路径，
      digest.py 走 window_items、不直接读 items）

⑤ 遗留：items 批内去重（produced 落库前按 (title, event_ts, group_id) 去重）
```

### 4.2 M6 · 配置从文件走到界面

## 5. 里程碑与出口标准

> 每个里程碑 = 一轮完整的「计划 → 实现 → 双层审查 → 冒烟 → 收尾 → 记忆埋点」。

### M5 · items 的正确性与可筛选性

**交付**：prompt v3、存量重判命令、`place`/`deadline` 两道闸门、`config/persons.toml`、
`/api/items` 多值筛选、前端「按人物筛选」、**人工干预层（D14）与软删（D15）**、批内去重。

**出口证据**（**尽量机械，能算的就不靠感觉**）：

1. **噪声**：「生活」类目里卡类占比 **34% → <5%**（同一口径重算，命令写进报告）
2. ⭐ **误杀为零**：§1.2 那 5 条（item 14/84/86/111/143 的**源消息**）在重抽后
   **必须仍然产出条目**。**这是本次改动的核心判据——它守的正是"D13 为什么不能按 uid 屏蔽"这件事。**
   变异反证：把 prompt 里那条"入"改成"不入"（或把 `deadline` 时序闸门反向），判据必须变红。
3. **要素**：重抽后不再存在 `deadline_ts < event_ts` 的条目（当前 1 条）
4. **人物**：`config/persons.toml` 录一个真实 uin，前端能筛出它发过的条目；复选 2 个人 = 并集；
   与类目复选叠加 = 交集
5. **幂等**：重抽命令跑两次，items 不重复增长
6. ⭐ **人工干预层**（D14/D15）：
   - 在网页改一条 item 的分类 → 前端与**日报**两处都跟着变（**只验前端不验日报 = 漏检 R13**）
   - 删一条 item → 界面消失、库里的行**仍在**（机械核对 `SELECT count(*)`）
   - **撤销** → 恢复原状
   - ⭐ **删除后跑 `vigil refine --redo`，被删的条目不得复活**（D15 的**唯一**机械判据，
     也是 `refine.py` 读 overlay 这条改动的变异反证点）
   - **`data/vigil.db` 全程保持 `mode=ro`**（反向验证：让端点故意写一次，守卫必须变红）

### M6 · 配置从文件走到界面

**出口证据**：

1. 网页上能新增一个群、一个人，落盘到 `config/*.toml`，**重启后仍在**
2. **机械不变量**：`data/vigil.db` 仍 `mode=ro`，且**新增的测试能证明 Web 端点没写过 `data/`**
   （D11 的守卫；反向验证：故意让端点写一次 `data/`，守卫必须变红）
3. LLM 配置切到一个自填 base_url 后，`vigil refine` 与 `vigil digest` **两处都生效**
4. 导出的配置包在**另一个目录**能导入并生效（用临时数据根验证，不碰真库）
5. U-4 修复后，`groups` 与 `export` 并发跑不再互相破坏（对照实验：修复前必现、修复后消失）
6. **类目编辑**：网页里加一个类目 → `vigil refine` 立刻认得它（`known_kinds` 跟着变）；
   删一个类目 → 提示"有 N 条属于它"，且**不允许静默留下指向不存在 slug 的条目**
7. **重排**：改类目定义 → 重判已有条目 → 结果落 overlay；**`items.item_id` 前后不变**（D16 的机械判据）；
   重排后**撤销**能回到重排前

### M7 · 外观

**出口证据**：

1. 五套主题**人眼验收**（用户本人判定，对齐 M1「抽样 100 条人工验收」的既有做法）
2. 切换后刷新页面仍在（持久化）
3. **手机 PWA 下五套都不白屏**，且新版本部署后**无需手动清缓存**
4. 浅色主题下无「深色残留」（`bg-black/30` 一类必须先被语义变量替换）

## 6. 风险与未验证项

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R8 | **prompt v3 会误杀合法条目** | 直接违背 M5 出口判据 2 | 出口判据 2 就是为它设的：**5 条已知好条目必须活下来**。重抽前先备份真库（沿用 M4 的 `db.bak` 惯例） |
| R9 | **重抽会改变 item_id** | 既有 `digest_items` 引用旧 id | ✅ **已实测收窄 + 已由 D16 化解**：<br>实测：`digest_items` 共 66 行指向 66 条，**那 46 条广告 item 被日报引用的 = 0 条**。<br>**D16 之后「重排」走 overlay 的 `set_kind` 事件、不碰 `items`** ⇒ **`item_id` 不变**，R9 对重排不再成立。<br>残余风险只在 §4.1 ① 的存量重判：语义已定为「**只删不换**」+ 被引用者跳过并报告。<br>另：`items` 用 `INTEGER PRIMARY KEY`（非 AUTOINCREMENT，`sqlite_sequence` 为空），新条目从 `max+1` 起 |
| R10 | M6 的配置写路径引入并发写 | 两个请求同时写 `config/*.toml` → 丢更新 | 原子写 + 单文件锁；（单用户自用，概率低，但**不能因为概率低就不做原子写**） |
| R11 | 主题重构面比预估大 | M7 超期 | §1.5 已实测收窄了范围（13 行 CSS + 几十处 className，**不是**全站重写）。若超期，**砍到 3 套主题**（默认 + material + 蒸汽波）而不是砍质量 |
| R12 | **`enable_thinking` 在非 SiliconFlow 端点上报错** | M6 出口判据 3 失败 | 该字段设计成可选（`None` 时不发），M6 计划里必须有「非 SiliconFlow 端点的报文形态」测试 |
| **R13** | ⭐ **overlay 覆盖不全**（本版最大的系统性风险） | **同一件事在两处显示不同**——最典型的形态是「界面上删了、日报里还在」 | ✅ **已实测量化并给出结构性缓解**：真读路径只有 **5 处**（§3.3 的表），且 **`digest.py` 不直接读 items，它走 `store.window_items`** ⇒ **把 apply 收敛进 `store.py` 的查询函数，而不是在各消费方打补丁**。一处生效，所有消费方继承。<br>若反过来在消费方 apply，就是本风险；M4「**记下来了 ≠ 派下去了**」的同族：**漏掉的那一处不会有任何测试变红**。<br>出口判据：M5 判据 6 要求「前端**与日报**两处都验」（只验前端 = 漏检） |

## 7. 不做的（明确排除，避免范围蔓延）

| 主题的自定义色板编辑器 | 五套预设够用 |
| 富消息段解析器 / 图片 OCR | 沿用第一版 §8.1、§9 |
| 增量导出 | 沿用第一版 §9（实测全量重读仅 2.9 秒） |

## 8. 与第一版的关系

- 第一版 §4.3（类目体系）、§4.5（脱敏）、§4.6（日报）、§4.7（Web）、§4.8（自动化）**全部继续有效**。
- 本版**只改一处既有设计**：M3 的机械不变量「Web 侧绝不写 `data/vigil.db`」
  → **细化为「可写 `config/` 与人工干预层，不可写 `data/vigil.db`」**（D11 + D14）。
  **注意：细化的方向是"更精确"，不是"更松"**——原表述挡不住「我可以写 `data/cache/` 啊」，
  而 §1.6 那个地雷正是这个形态。新表述把边界钉在**具体文件**上。
- 本版**新增一条判据**：§3.4 的「要素归属判据」——语义归 prompt，格式/证据/时序归 code，
  **没有 code 闸门的要素字段不算做完**。
- 本版**新增一个结构性风险**：R13（overlay 覆盖不全）——它是 M4「记下来了 ≠ 派下去了」的同族：
  **漏掉的那一处读路径不会有任何测试变红。**
