## 1. 现状实测

> **快照时刻 2026-10-10 下午（UTC+8）。** 库会自己涨（每日 08:00 管线），
> 要用请现查。本节所有数字均来自 `data/vigil.db`（`mode=ro` 只读连接）。

### 1.1 ⭐ 截止日极其稀疏：592 条 items，只有 36 条带截止日（6%）

```
uv run python -c "import sqlite3;c=sqlite3.connect('file:data/vigil.db?mode=ro',uri=True);
print(c.execute('SELECT COUNT(*), COUNT(deadline_ts) FROM items').fetchone())"
⇒ (592, 36)
```

分布（按本机时区 UTC+8 取 `date`）：

```
2026-08-26  1   2026-09-19  1   2026-11-22  1
2026-09-06  2   2026-09-22  2   2026-11-29  1
2026-09-11  1   2026-09-24  8   2026-12-25  1
2026-09-13  1   2026-09-25  4
2026-09-14  1   2026-09-29  1
2026-09-15  2   2026-10-15  1
2026-09-16  6   2026-10-26  1
2026-09-18  1
```

**这是设计要接受的前提，不是缺陷**：日历的大多数格子会是空的。
⇒ 日历的**默认落点必须是「今天所在月」**（用户裁定 Q3），而不是"最近一个有截止日的月"——
后者会让用户以为日历跳错了时间。

### 1.2 ⭐⭐ 截止日**全部只到「日」精度**：36/36 的时刻恰为 `00:00`

```
uv run python -c "…SELECT deadline_ts FROM items WHERE deadline_ts IS NOT NULL…"
⇒ 全部 36 条的 hour==0 and minute==0
```

**这条改变了日历的显示契约。** 数据里根本不存在"几点几分到期"的信息，
所以日历**绝不许**渲染「00:00 到期」或任何时刻——那是**把精度不足伪装成精确**，
正是本项目反复记过的那条产品级判据（「只说自己有资格说的话」）的反面。
**日历的粒度是「日」，仅此而已。**

### 1.3 ⚠️ 接力文件里那条不变量**已经失效**，本 spec 如实更正

`docs/superpowers/progress/vigil-progress.md` §二 写：

> ④ `deadline_ts < event_ts` 的条目 = **0**

**实测现在是 4/36**（该文件刻于 2026-09-22，期间数据变了）：

```
item 403  event 2026-09-15 17:45  deadline 2026-09-15 00:00  大学团学思想教育讲座
item 406  event 2026-09-16 18:13  deadline 2026-09-16 00:00  心理健康教育专题讲座
item 530  event 2026-09-22 08:03  deadline 2026-09-22 00:00  四六级报名今日17:00截止
item 532  event 2026-09-22 08:38  deadline 2026-09-22 00:00  四六级报名今日截止，请抓紧缴费
```

**这 4 条不是真的倒挂**：它们的 `deadline` 与 `event` 是**同一天**（如 530：当天 08:03 发、
"今日 17:00 截止"），而截止日被存成了当天 `00:00` ⇒ 时刻上先于 event。
根因就是 §1.2 的日粒度。

⇒ **本 spec 不把「deadline ≥ event」当不变量**（它在日粒度下本就不该成立）；
日历**显示层**也不因此做特殊处理——「今天到期」的条目出现在「今天」格子里，
与它几点发布无关。（将来若要恢复这条不变量，须先把 `deadline_ts` 的语义定成
"当天结束 23:59"或"当天零点"，那是另一件事，本版不做。）

### 1.4 `/api/items` 的 `limit` 上限是 **200**

```
vigil/api.py:51  MAX_LIMIT = 200
```

⇒ **前端无法靠 `/api/items` 拿全量截止日**（今天 36 条够，但每个 200 条的限制是死线，
且前端硬筛要先把整个窗口的 items 拉回来）。**日历必须有自己的端点**（§3.1）。

### 1.5 前端运行时依赖只有 3 个，且**全仓零 IndexedDB 用法**

```
dependencies: react 19.3.0 / react-dom 19.3.0 / react-markdown 10.1.0
grep -rn "indexedDB\|localforage\|idb" web/src/  ⇒ 空
```

现有持久化**只有 localStorage**（`theme.ts` 的 `vigil.theme`、`uiState.ts` 的 `vigil.view`）。

### 1.6 ⭐ 快照的真实体量 ≈ **47 KB**，localStorage 绰绰有余

按用户裁定的边界（最近 5 天信息流 + **全量**截止日 + 最近 5 篇日报）粗估：

| 分量 | 量 |
|---|---|
| 最近 5 天 items | 23 条 |
| 全量带截止日 | 36 条 |
| 最近 5 篇日报 `body_md` | 合计 ≈ 1.3 KB（单篇 99–431 B） |
| **估算序列化总量** | **≈ 47 KB** |

vs **localStorage 上限约 5 MB** —— 只用了**不到 1%**。

⇒ **决策：用 localStorage，不用 IndexedDB。** 引入 `idb` 依赖 + 异步事务
在这个体量下是**过度设计**（用户 Q1 已授权"若技术上不合理就告诉我"——
这里的不合理恰恰是**反过来**的：IndexedDB 才是多余的那一侧）。

### 1.7 离线相关：更新链路 M7 已做完；但 **SW 不缓存 API**，且**没有在线/离线探测**

- **更新链路已完整**（M7）：`vite.config.ts` 用 `registerType:'prompt'` + `main.tsx` 的
  `registerSW({onNeedRefresh})` + `SwUpdateToast.tsx`。本版**不需要**碰它。
- ⚠️ **关键约束**：`vite.config.ts` 的 `workbox.navigateFallbackDenylist = [/^\/api\//]`
  ⇒ **Service Worker 不会把 `/api/` 请求兜底缓存**。所以离线数据**只能**由应用层
  （localStorage）持有，不能指望 SW。
- **全仓没有 `navigator.onLine` / `online` / `offline` 监听**：

  ```
  grep -rn "navigator.onLine\|'online'\|'offline'" web/src/  ⇒ 空
  ```

  ⇒ 在线/离线状态机是本版**新增**的东西，且它是"静默降级 vs 明确告知"的分界点。

## 2. 目标与成功标准

**目标**：让 VIGIL 的 PWA 能（a）**按天**看到期的事，（b）在**电脑关机/断网**时
仍能浏览最近同步过的信息——且**不假装**那些数据是实时的。

**成功标准**（= §5 出口标准，用户判定）：
1. 五套主题 + ARGUS 下日历都正常（不白屏、无色漏、点得到）。
2. 断网后信息流/日历/日报**仍可浏览**，并**明确标注**这是何时同步的快照。
3. 断网时**写操作不可用**（置灰 + 提示需联网）。
4. 网络恢复后**自动**回到实时数据。
5. 快照**不把"离线不知道"谎报成"真的没有"**（空 ≠ 未知）。

## 3. 设计

### 3.1 后端：新增日历端点 `GET /api/calendar`

```
GET /api/calendar?from=YYYY-MM-DD&to=YYYY-MM-DD
```

- **只回带截止日的条目**，按 `(date(deadline_ts), event_ts, item_id)` 升序。
- 字段复用 `api.py:724` 的 `item_out(...)`（与 `/api/items`、`/api/digests/{id}` 同形，
  前端 `Item` 类型一字不改）。
- `from`/`to` 都可省 ⇒ **默认全量**（用户 Q1 裁定"日历保持全量"）。给了就按
  `[from, to]` **包含端点**过滤（与 `/api/items` 的 `since/until` 同口径，
  `api.py:135-168` 的 `_day_start` 复用）。
- 返回体：`{"items": [...], "total": N}`。**不分页**——截止日是全库最稀疏的一类
  （§1.1），但当它真的涨到需要分页时，这个端点的 `total` 就是触发器。

**为什么自成一端（而不是前端筛 `/api/items`）**：§1.4 的 200 上限 + 前端硬筛要把
整个窗口的 items 拉回来。**这是本项目"数据层"的一贯形状**——判据/过滤放在能被
后端测试直接守的那一层（对照 `deadline.py` 顶部注释的主线）。

**不变量（后端测试守）**：端点返回的每一条 `deadline_ts IS NOT NULL`；
升序；窗口过滤各自成立；**看不见的软删条目不出现**（复用 `store._NOT_DELETED`）。

### 3.2 前端：「日历」tab（第 5 个）

- `uiState.ts` 的 `TABS` 加 `{key:'calendar', label:'日历'}`，`Tab` 联合类型加 `'calendar'`。
  ⚠️ **`readView` 的 `VALID_TABS` 自动跟上**（它由 `TABS` 派生）——旧 localStorage 里
  存的 `tab` 若不在新集合里会回落 `feed`，这是**已有行为**，本版不新增逻辑。
- 新视图 `web/src/views/Calendar.tsx`：
  - **月历网格**（7 列），默认落在**今天所在月**（Q3）。可翻月。
  - 每格：日期数字 + **有截止日就打点**。到期的点**实心**、**已过期的点变淡**
    （用户 Q2：以变淡区分；具体用哪个 `--v-fg-*` token 在计划期定，**不许裸色**）。
  - 点某天 → 该天到期条目列表（复用 `ItemCard`）。点条目进现有的详情。
- **主题**：全部走 `--v-*` 语义 token（M7 已建立，`noRawPalette.test.ts` 会守）。
- **数据**：走 §3.1 的端点。离线时回落到快照（§3.3）。
- ⚠️ **不许显示时刻**（§1.2）：格子与列表只说"哪天到期"，不出现 `00:00`。

### 3.3 前端：离线快照 `web/src/snapshot.ts`

**存什么**（用户 Q1）：`{synced_at, feed_recent, calendar_items, digests_recent}`

| 字段 | 内容 | 边界 |
|---|---|---|
| `feed_recent` | 信息流首屏数据 | **最近 5 天**的 items |
| `calendar_items` | 日历数据 | **全量**（§1.1 稀疏，§1.6 体量够） |
| `digests_recent` | 最近日报（含 `body_md`） | **最近 5 天** |
| `synced_at` | Unix 秒 | 快照生成时刻，**展示时要用** |

**写**：每次**在线**成功取数后写一次（一个 JSON，key 如 `vigil.snapshot`）。
**不引入 IndexedDB 依赖**（§1.5/§1.6）。

**读（回落顺序）**：先走网络 → **失败**才读快照 → 两者都没有 ⇒ 说"没有数据"。
⚠️ **必须把三种状态分开**（这是本项目「只说自己有资格说的话」的直接应用）：
1. 网络通、真没有 ⇒ "还没有条目。"
2. 网络断、有快照 ⇒ "这是 **{synced_at 时刻}** 的快照。"
3. 网络断、无快照 ⇒ "离线，且还没有本地快照。"

**写操作**：离线时置灰 + 提示"需要联网"（§3.4）。快照**只读**。

### 3.4 前端：在线/离线状态机

- 新模块（如 `web/src/connectivity.ts`）持有 `online` 状态：
  - 初始值 `navigator.onLine`；
  - 监听 `window` 的 `online` / `offline` 事件；
  - ⚠️ **`navigator.onLine` 不可全信**（它只说"有没有网卡/链路"，不说后端可达）——
    所以**以"请求是否真的失败"为准**，事件只是提前量。这是本设计里最容易写成
    "设置对了 ≠ 行为对了"的地方，**取证要分开**（对照 M4 教训）。
- 恢复在线时：视图**自动**重取实时数据（出口标准 4）——不是卡在快照上。
