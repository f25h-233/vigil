# 可行性评估：笔记本登录 QQ 监听指定群 + 实时解析 + 不耽误 PC 端 QQ

调研日期：2026-09-13 ｜ 证据来源：NapCat 官方文档仓库 `NapNeko/NapCatDocs`、NapCatQQ Releases API、GitHub 搜索结果。原始数据在同目录。

---

## 一、可行性结论

**按常规 NapCat 部署——做不到。会互踢。**

### 为什么

NapCat 官方文档的架构图写得很清楚：

```
NTQQ客户端  --JavaScript API调用-->  NapCat核心
NapCat核心  --事件注入----------->  NTQQ客户端
```

即：**NapCat 不是一个独立程序，它寄宿在一个 QQ NT 客户端进程内**，通过调用 QQ 自己的 Node 模块接口来收发消息。

推论链：
1. NapCat 跑起来 = 多了一个「电脑端 QQ 在线」
2. QQ 的多端策略：手机 + 电脑可同时在线，但**同一账号只能有一个电脑端**
3. 所以 NapCat 登录后，你笔记本上的 QQ 会被踢；你打开 QQ 又会把 NapCat 踢下线

**佐证**（NapCat 仓库 issue 搜索）：
- 「被踢下线」是高频问题，官方甚至有 `[FEAT] 支持账号被踢下线时执行自定义 Hook` 这种需求
- `[BUG] 最新版本的 NapCat/QQ 登录会被风控检测导致频繁掉线`

### 官方安全文档的额外警告

> **避免在同一 IP/设备上同时登录 Bot 账号与常用账号，以防常用账号受到异常影响**
> 遇到社交风控时，解除限制后重新运行即可

注意这句话的**预设是「Bot 账号 ≠ 常用账号」**。你想用的方案是**大号本身当 bot**，等于把这个隔离直接取消——风险高于官方警告所针对的场景。

## 二、三条能走的路（各有一个代价）

### 路线 A：LiteLoaderQQNT 插件形态 —— 唯一真正「不耽误」

**原理**：把 `NapCat.Framework.zip` 导入 LiteLoaderQQNT，NapCat 作为插件跑在**你正在使用的那个 QQ 客户端**里。你开的就是同一个 QQ，没有第二个客户端，**不抢登录位**。
→ PC 端 QQ 照常聊 ✅，NapCat 在进程内旁听 ✅

**证据**：`NapCat.Framework.zip` 在最新版 v4.18.19（2026-08-14）仍在正常发布。

**代价**：NapCat 官方文档明写——
> 自 QQ 9.9.19 后 LiteLoaderQQNT 维护欠缺，NapCatQQ 鼓励用户迁移到 Shell 版本，其官方的修补方式与安装方式不再推荐。

属于「能跑但官方不背书」。LiteLoaderQQNT 本体 7103★、最后更新 2026-05-09；生态仍有插件在跟版本（如 `ltxhhz/LL-plugin-list-viewer` 2026-09-13），但整体在追 QQ 版本，QQ 大更新后有失效风险。

### 路线 B：NapCat 放另一台常开设备 + 改用手机看 QQ

服务器/旧电脑跑 NapCat 会占掉「电脑端」登录位 → 你笔记本的 PC QQ 登同号**很可能互踢**（此点我未实测，逻辑上与路线 A 的冲突同源，建议实测确认）。
但你**手机 QQ 照常收发** ✅

**代价**：放弃 PC 端 QQ。

### 路线 C：本地数据库旁路 —— 零登录冲突，但非实时

QQ NT 的消息落在本地加密 SQLite，现有工具能解密导出：
`QQBackup/QQDecrypt`(230★)、`Mythologyli/qq-nt-db`(147★)、`QQBackup/nt_msg_db_util`(16★)、`2233admin/qqcli-rs`(11★，Rust CLI)

**但没有实时监听方案**。搜索证据：
- `"QQ 聊天记录 实时解析"` → **0 个结果**
- `"QQ 消息 实时 监听"` → **2 个结果**，且都基于 NapCat

**代价**：要自己写轮询 + 增量解析，且要面对数据库加密与 QQ 版本变化。

## 三、一个你可能低估的点：小号其实没那么难

你说「那些传达消息的群不太可能让机器人进去」。但对**通知群/班群**来说，管理员不会挨个验证「这个号是不是机器人」。小号只要**表现得像人**（不改头像、不改昵称、不发言、只读），通常没人会注意到。

如果能接受小号，路线立刻变宽：
- 小号跑 NapCat 占掉电脑端 → **你大号在 PC 上照常聊，两边完全不冲突** ✅
- 这是社区标准做法，也正是官方安全文档假设的场景（Bot 号与常用号分离）

**代价**：新增一个 QQ 号的注册与养号成本。

# 六、路线 C 的时间成本（追加，2026-09-13）

## 实测：你自己的数据库有多大

实测本机 `C:\Users\qwe13\Documents\Tencent Files\1307553675\nt_qq\nt_db`：

| 文件 | 大小 | 说明 |
|---|---|---|
| **`nt_msg.db`** | **2.94 GiB** | 消息主库（加密 SQLCipher） |
| **`group_msg_fts.db`** | **0.85 GiB** | QQ 自建的群消息全文索引 → **你约 90% 的内容是群消息** |
| `profile_info.db` / `group_info.db` | 各 ~0.05 GiB | 资料/群信息 |
| **目录合计** | **3.93 GiB** | |

这个数字直接决定了节奏是否可行。

## 分阶段耗时

| 阶段 | 单次耗时 | 频率 |
|---|---|---|
| **密钥提取** | 秒级（内存扫描/Frida 注入）；或一次性拿到后复用 | 一次性 / 每次几秒 |
| **全量解密**（`sqlcipher_export`，`qq-nt-db` 路线） | 读 2.94 GiB + 写 2.94 GiB ≈ **1–3 分钟**（NVMe 顺利时） | ❌ 一天几次不可接受，且需额外 2.94 GiB 磁盘 |
| **若触发数据库修复**（`qq-nt-db` 明确警告 "database disk image is malformed" 很常见） | `.dump` 成 SQL 文本再重建 → **10 分钟起步** | ❌ |
| **原地带密钥查询**（SQLCipher 直接 open，只读增量） | **秒级**（只读命中页） | ✅ |
| **首次建全文索引**（qqcli-rs 的 `qq index`，DuckDB） | 对 2.94 GiB 语料，估 **数分钟** | 一次性 |
| **索引后增量查询**（`qq history <id> --since ...` / `qq search`） | **秒级** | ✅ 一天几次完全可行 |

> ⚠️ 除"实测的库大小"外，上表耗时是按磁盘 I/O 与 SQLCipher 吞吐做的**估算**，未实测。

## 结论

**你的节奏（一天几次 + 手动唤起）合理，但只成立于「增量」模式。**

- 一次性成本：解密 + 建索引，按 2.94 GiB 量级估 **5–30 分钟**
- 之后的每次更新：**秒级到十几秒** ✅

**大幅提速的杠杆**：只处理你关心的那几个群。消息在 `group_msg_table` 里可按群号过滤，把 2.94 GiB 缩到几 MB，全量也变秒级。

## 最匹配的现成工具

**`2233admin/qqcli-rs`**（11★，Rust，2026-08-18，Windows）—— 设计正好是增量式：
- `qq init` → 发现账号、检查库，需要解密时请求 **one-time** 授权
- `qq index` → 建全文索引（DuckDB）
- `qq history <id> --since 2024-01-01` / `qq search "关键词"` → 查索引，**不重复解密**
- 关键优势：**"QQ must have run on the machine at least once"** → **不需要 QQ 常驻运行**
- 还带 `qq plugin send`（可选 NapCat 集成）做发送

## 风险（必须知情）

1. **11★ 新项目**（2026-08-18），无社区验证
2. **QQ 版本兼容**：同类的 `qq-nt-db` 只验证到 QQ `9.9.12-26339`（2023 年代），你的 QQ 大概率更新了
3. **官方级警告**（QQBackup 原话）：这类工具「**可能破坏聊天记录或导致封号**」；建议先备份、优先在虚拟机/不常用设备操作、尽量选择不注入 QQ 进程的方式
4. 消息正文在 `group_msg_table` 的 `40800` 字段里是 **Protobuf 二进制**，解析需额外工作

## `QQBackup/qq-win-db-key` —— 全平台密钥提取脚本集

对应 §六耗时表的第一行（"密钥提取：秒级（内存扫描/Frida 注入）"）。它在整个路线 C 里的位置是**第一道门**：拿不到密钥，后面 `nt_msg.db` 就是一堆密文。

**仓库定位**：只放**代码**，不放教程。分平台脚本：

| 目录 | 覆盖 |
|---|---|
| 根目录 | 各平台密钥提取、数据库导出、重加密脚本 |

**教程正文不在这里** → 统一在 `QQDecrypt` 文档库（在线：`qqbackup.github.io/QQDecrypt`）。

**⚠️ 项目自述的门槛与风险（原文意思）：**
- **不是面向小白的完整教程**，假定使用者具备**逆向、动态调试、脚本修改**能力；脚本通常要按 QQ 版本/系统环境/安装情况自行调整
